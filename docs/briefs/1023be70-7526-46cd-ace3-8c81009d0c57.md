## Central hypothesis

Deterministic simulation testing may have a useful boundary above the OS/VM but below application correctness logic.

The original proposed boundary was:
```text
application correctness logic
        ↓
network / storage / time / entropy / lifecycle / cooperative scheduling
        ↓
deterministic simulator
```

Previous analysis found that this is incomplete.

The harder boundary may be:
```text
application correctness logic
        ↓
controlled execution continuations
        +
controlled external effects
        ↓
deterministic simulator
```

The key hypothesis is therefore:

> A deterministic testing platform can preserve substantial correctness-critical production implementation if it controls external effects and selected execution suspension/resumption points, without requiring either a simulator-specific rewrite or whole-OS deterministic execution.

I want you to determine whether this is actually true.

# The central unresolved problem

Suppose production code contains:
```text
foo()
    ↓
write(...)
    ↓
fsync(...)
    ↓
update metadata
    ↓
return
```

and `write`/`fsync` are synchronous from the application's point of view.

A deterministic simulator needs the ability to explore:
```text
write submitted
another node runs
write partially/effectively happens
node crashes
write completion delayed
storage becomes/not becomes durable
original execution resumes
```

without rewriting `foo()` into an explicit simulator state machine.

The current Adversary reactor model instead roughly requires:
```text
node.step()
    ↓
io.submit()
    ↓
return from node.step()
    ↓
simulator runs effects
    ↓
later node.step(completion)
```

That works naturally for async/event-driven software.

It may fail badly for existing synchronous call graphs.

This continuation question may determine whether Adversary represents a genuinely distinct architecture or merely another deterministic runtime for already-structured async software.

# 3. The decisive Wasm question

Try to construct this minimal implementation:
```rust
fn commit(tx: Tx) -> Result<()> {
    encode(tx)?;
    file.write_all(bytes)?;
    file.sync_all()?;
    publish_commit(tx)?;
    Ok(())
}
```

Assume this function is synchronous production code.

Design a deterministic execution where:

1. `file.write_all()` enters the host.
2. The guest execution suspends without unwinding.
3. Another simulated node executes.
4. Part of the write takes effect.
5. A crash is considered at that point.
6. Persistence may or may not advance.
7. The write completion becomes available.
8. The original stack resumes.
9. `write_all()` returns.
10. Execution reaches `sync_all()`.
11. The simulator again gains control.
12. Exact replay reproduces all decisions.

Determine whether this is possible with current Wasmtime/Component Model technology.

- explain whether stack state can be discarded cheaply,
- explain how multiple suspended nodes coexist,
- explain whether runtime scheduling introduces hidden nondeterminism,
- explain whether guest threads break the model.

# 5. Scheduling granularity

The previous architecture treated one Future poll or guest turn as atomic.

That misses ordinary races such as:
```rust
let x = *state.lock();
*state.lock() = x + 1;
```

where production threads may interleave between the two lock acquisitions.

Investigate whether any proposed architecture can expose scheduling points:

- at async waits only,
- at synchronization operations,
- at host imports,
- at explicit yields,
- at function boundaries,
- through compiler instrumentation,
- using Wasm fuel,
- at arbitrary instruction boundaries.

For each level determine:

- fidelity,
- implementation cost,
- state-space explosion,
- replay complexity,
- runtime dependence.

The goal is not instruction-level simulation unless the evidence shows it is necessary.

Find the coarsest execution boundary that still preserves most consequential correctness behavior for the intended user.

# 8. Re-evaluate Wasm's architectural role

At the end, choose among these conclusions:

### H1

### H2

The necessary Wasm/runtime machinery becomes so complex or semantically different from production that the benefit disappears.
