# Current surviving hypothesis

Previous investigation established that Wasmtime can suspend an unchanged synchronous guest call at a host import while the deterministic host schedules other nodes and controls external effects.

An unmodified redb 4.1.0 transaction/recovery implementation was successfully executed this way with zero source modifications to redb.

Therefore the question:

> "Can synchronous production code survive the continuation boundary?"

has a positive answer for at least isolated synchronous storage owners.

That is no longer the central uncertainty.

The remaining hypothesis is:

> For a real distributed infrastructure implementation with nontrivial task/worker structure, Adversary can preserve the correctness-critical production implementation while controlling enough continuations, synchronization points and external effects to expose consequential safety bugs, at an integration cost and exploration quality competitive with existing deterministic runtimes.

The decisive issue is no longer API compatibility.

It is **execution-topology preservation**.

# 2. Define the exact safety properties

Do not test merely for crashes.

At minimum define:

## P1 — durable acknowledgment

If a client operation is reported committed under the application's contract, the value must remain recoverable under the declared surviving-quorum fault model.

## P2 — Raft vote persistence

A node must not issue votes inconsistent with its durable term/vote state after restart.

## P3 — committed log safety

An entry considered committed must not disappear from every surviving legal recovery state.

## P4 — snapshot/log publication

A crash during snapshot or log rotation must not leave a state that loses acknowledged operations.

## P5 — retry/deduplication

A lost response followed by retry must not cause an illegal duplicate application effect.

Add project-specific properties discovered during source inspection.

Use an independent checker where feasible.

Do not trust internal state alone.

# 14. Predeclared kill criteria

Treat these as falsification, not future work.

## Kill K1 — execution topology

If preserving the real WAL worker requires replacing its batching/concurrency architecture, Adversary fails for this target.

## Kill K2 — integration burden

If the integration requires substantial modifications to consensus/storage correctness logic rather than boundary extraction, the claimed sweet spot is too narrow.

## Kill K3 — competitor dominance

If Commonware, Turmoil or MadSim produces equivalent bug coverage and replay with less than roughly half the integration effort and Adversary provides no demonstrated containment/diagnostic advantage, do not build a separate runtime platform.

## Kill K4 — Wasm irrelevance

If the same production paths are easier to preserve natively and Wasm provides no concrete benefit for this target, make Wasm optional.

## Kill K5 — Wasm distortion

If the bugs disappear because compilation to Wasm removes the relevant worker, dependency, synchronization or runtime behavior, the Wasm execution does not count as preservation.

## Kill K6 — scheduling insufficiency

If important in-scope historical defects require interleavings inside units Adversary treats as atomic, either add justified synchronization scheduling or exclude the target.

Do not simply add arbitrary instruction scheduling.

## Kill K7 — storage correspondence

If native storage outcomes cannot be represented economically by the claimed profile, do not market that profile as production-corresponding.

## Kill K8 — exploration non-result

If semantic exploration provides no measurable improvement over ordinary randomized deterministic scheduling at equal compute budgets, remove exploration superiority from the thesis.

## Kill K9 — debugging non-result

If semantic traces do not measurably improve diagnosis, remove debugging superiority from the thesis.

## Kill K10 — product economics

If a capable infrastructure project requires months of bespoke adaptation and ongoing compatibility maintenance comparable to maintaining its own simulator, the reusable-product hypothesis fails.

# 15. What counts as positive evidence?

Do not declare success because the target runs.

Strong evidence requires all of these:
```text
real correctness implementation preserved

AND

real execution topology relevant to tested invariants preserved

AND

multiple consequential historical bugs or faithful mutants represented

AND

reliable replay

AND

native outcomes support the claimed environment profile

AND

integration cost is competitive

AND

Adversary provides at least one measurable advantage over existing runtimes
```

The desired result could therefore be:

> The continuation hypothesis survives but Adversary should be a Commonware extension.

That is a valid outcome.

Or:

> Suspended Wasm owners materially reduce integration effort for storage engines while preserving fault visibility unavailable in existing runtimes.

That is also valid.

Or:

> The worker/runtime semantics are too important; deterministic native execution is the better boundary.

That is also valid.
